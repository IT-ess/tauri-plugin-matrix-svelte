# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Tauri v2 plugin that wraps [matrix-ui-serializable](https://github.com/IT-ess/matrix-ui-serializable) (itself a
wrapper around `matrix-rust-sdk`) and exposes a high-level Matrix client to a Svelte 5 frontend via Rune stores.
Works on desktop and mobile (Android/iOS). The plugin is split into a Rust half (`src/`, `android/`, `ios/`) and a
JS/Svelte half (`guest-js/`, published as the `tauri-plugin-matrix-svelte-api` npm package). `example/matrix-svelte-client`
is a full reference Tauri app that consumes the plugin and is the best place to see end-to-end usage.

## Sibling repo dependencies (important)

This repo is expected to be checked out alongside two sibling repos at the same directory level:

- `../matrix-ui-serializable` — the core Matrix client logic (referenced via `path = "../matrix-ui-serializable"` in
  `Cargo.toml`). All the domain types re-exported from `src/lib.rs` and every file under `guest-js/lib/bindings/`
  come from here.
- `../tauri-plugin-notifications` — push notification plugin (referenced via `path = "../tauri-plugin-notifications"`).

Both the plugin's `Cargo.toml` and the example app's `example/matrix-svelte-client/src-tauri/Cargo.toml` depend on
these by relative path, not by version/git. If either sibling is missing, `cargo build`/`cargo check` fails immediately.

`guest-js/lib/bindings/*.ts` are generated by [ts-rs](https://github.com/Aleph-Alpha/ts-rs) from Rust types in
`matrix-ui-serializable` — never hand-edit them; regenerate from the sibling repo instead.

## Common commands

Plugin (repo root):
- `pnpm install` then `pnpm build` — builds the JS/Svelte bindings package (`svelte-package` + `publint`)
- `pnpm check` — `svelte-kit sync` + `svelte-check`
- `pnpm lint` / `pnpm format` — prettier + eslint (check vs. write)
- `cargo build` / `cargo check` — builds the Rust plugin (requires sibling repos, see above)

Example app (`example/matrix-svelte-client`):
- `pnpm install`
- `pnpm tauri dev` / `pnpm tauri build` — run/build the full desktop app
- `pnpm check`, `pnpm lint`, `pnpm format` — same tooling as the plugin package
- Mobile: standard `pnpm tauri android dev` / `pnpm tauri ios dev` once the platform projects are initialized

There is no JS test runner wired up (vitest is a dependency but no `*.test.*`/`*.spec.*` files exist yet). Rust has a
couple of inline `#[test]`s (e.g. `reconstruct_custom_uri` in the example's `src-tauri/src/lib.rs`); run with
`cargo test`.

## Required plugin configuration

Consumers must set a `matrix-svelte` key in `tauri.conf.json`'s plugin config with: `android_sygnal_gateway_url`,
`ios_sygnal_gateway_url`, `oauth_client_uri`, `oauth_redirect_uri` (see `PluginConfig` in `src/lib.rs`).

This plugin must be initialized *after* `tauri-plugin-svelte` and `tauri-plugin-notifications` in the consuming
app's builder chain — it depends on both being ready first.

## Architecture

### Rust plugin core (`src/`)

- `lib.rs` — plugin entry point (`init()`), registers all commands, spawns the async matrix-ui-serializable runtime
  during `setup`, wires up the `LibConfig` (session, event receivers, updaters, OAuth config). Also holds two global
  `OnceLock` senders (`LOGIN_SENDER`, `AUTH_DEEPLINK_SENDER`) used to bridge frontend-triggered events into the async
  runtime, and re-exports the domain types/commands consumers need.
- `commands.rs` — all `#[tauri::command]` handlers invoked from JS (`invoke('plugin:matrix-svelte|...')`).
- `desktop.rs` / `mobile.rs` — platform split for `MatrixSvelte<R>` construction; mobile registers the native
  Android (`PushNotificationPlugin`) / iOS (`init_plugin_matrix_svelte`) plugin handles.
- `events.rs` — two-way event bridge between the frontend and the matrix-ui-serializable async runtime:
  - Outgoing (`event_forwarder`): consumes `EmitEvent`s from a broadcast channel and re-emits them as Tauri events
    (`matrix-svelte://...`) or OS notifications.
  - Incoming (`handle_incoming_events`): listens for specific Tauri events from the frontend (e.g.
    `matrix-svelte://verification-result`) and forwards them into mpsc channels the core library reads from.
- `state_updaters.rs` — implements `StateUpdaterFunctions` (the `Updaters` struct). Every state change from the
  matrix client (rooms list, active room, login/verification/recovery state, current user info) is pushed to the
  frontend by patching `tauri-plugin-svelte` stores directly (ids: `rooms-collection`, `room-store`, `login-state`
  — these ids must match the JS store classes in `guest-js/lib/stores/`). This is a known architectural cost: full
  state is serialized on every update rather than diffed/streamed over raw IPC (documented in the README's
  "Possible improvements" section) — keep this in mind before "optimizing" one call site in isolation.
- `keyring/mod.rs` — persists the Matrix session using `keyring-core` with a platform-specific backend selected at
  compile time (macOS/iOS via `apple-native-keyring-store`, Android/Windows/Linux via their respective crates).
  Sessions are base64-encoded and namespaced with a random per-app-data-dir salt file. `init_keyring_store()` is
  idempotent (`std::sync::Once`) because it must be callable both from the normal plugin `setup` (warm path) *and*
  from the Android cold-start JNI entry point (see below) — `keyring_core::set_default_store` panics if called twice.
- `utils/mod.rs` — app dir resolution and plugin config parsing helpers.

### Frontend package (`guest-js/lib/`)

- `index.ts` — the public API surface: thin `invoke()` wrappers around every command, plus re-exports of stores,
  bindings, and event/type-guard helpers.
- `stores/` — the three Svelte 5 Rune stores consumers instantiate in `hooks.client.ts`: `RoomsCollection` (room
  list), `RoomStore` (currently open room/timeline), `LoginStore` (auth/login state). Their store ids
  (`rooms-collection`, `room-store`, `login-state`) are the other half of the contract with `state_updaters.rs`.
- `bindings/` — generated TS types mirroring Rust structs/enums from `matrix-ui-serializable` (see ts-rs note above).
- `matrix-requests/` — helpers to build `MatrixRequest` payloads for `submitAsyncRequest`.
- `tauri-events.ts` / `type-guards.ts` — typed wrappers for listening to the `matrix-svelte://...` events and
  narrowing timeline/message item unions.

### Mobile push notifications (silent/data-only pushes)

This is the most subtle part of the codebase — read `example/matrix-svelte-client/src-tauri/src/lib.rs`,
`push_handler.rs`, `push_shared.rs`, and the sibling `tauri-plugin-notifications`' `nse.rs` /
`TauriFirebaseMessagingService.kt` together before touching notification code:

- **One handler, every app state**: the example app registers a single Rust handler with the notifications
  plugin's `silent_push_handler!` macro (`push_handler.rs`). It exports both the iOS NSE `dlsym` entry and the
  Android JNI entry; the plugin's FCM service loads the app's `.so` itself (named by the `SILENT_PUSH_LIB`
  manifest meta-data) and calls the handler for every data-only push — warm *or* cold-started — then posts the
  returned `NotificationData`. The handler fetches the event via
  `tauri_plugin_matrix_svelte::handle_silent_notification` (`push_shared.rs`).
- **Android cold-start init**: a Firebase-started process never ran the plugin's `setup()`, so the macro's
  `android_init` hook (`android_push_init`) replays logging, `ndk_context`, the rustls platform verifier, and
  `init_keyring_store` before each handler run. `ndk_context` must only be initialized once per process; the
  guard is shared between this hook and the `initNdkContext` call from `MainActivity.onCreate` because Android
  may reuse the same process for both.
- **Badge pushes**: a data message without `room_id`/`event_id` is the homeserver's unread-count update; when
  `unread == 0` the handler returns `SilentPushResponse::ClearActive` and the plugin clears the notification
  shade plus its stored conversation histories (Android only — iOS badge pushes never reach the NSE).
- Android accumulates same-room notifications into one `MessagingStyle` notification (keyed by room id); iOS keys
  by event id and groups by conversation thread instead — this difference is intentional, not a bug.

### Custom `mxc://` media protocol

The example app's `src-tauri/src/lib.rs` registers an async URI scheme handler for `mxc://` to stream Matrix media
(including encrypted attachments, via query params for key/iv/hash) straight from the SDK into the webview. Android
and Windows can't route a fully custom scheme, so requests there arrive as `http://mxc.localhost/...` and get
rewritten to the common `mxc://...` form before parsing (`android_windows_to_common_uri`).

### Permissions (`permissions/`)

Tauri ACL definitions per command, one `allow-*` toggle per command in `permissions/default.toml`/`autogenerated/`.
When adding a new `#[tauri::command]` in `commands.rs`, it also needs a corresponding permission entry and to be
registered in `tauri::generate_handler!` in `lib.rs`.
