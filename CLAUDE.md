# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Tauri v2 plugin that wraps [matrix-ui-serializable](https://github.com/IT-ess/matrix-ui-serializable) (itself a
wrapper around `matrix-rust-sdk`) and exposes a high-level Matrix client to a Svelte 5 frontend via Rune stores.
Works on desktop and mobile (Android/iOS). The plugin is split into a Rust half (`src/`, `android/`, `ios/`) and a
JS/Svelte half (`guest-js/`, published as the `tauri-plugin-matrix-svelte-api` npm package). `example/matrix-svelte-client`
is a full reference Tauri app that consumes the plugin and is the best place to see end-to-end usage.

## Companion repo dependencies (important)

This repo builds against two companion repos, wired up two different ways:

- `matrix-ui-serializable` — the core Matrix client logic, referenced by **git** in `Cargo.toml`
  (`git = ".../IT-ess/matrix-ui-serializable"`; a `path = "../matrix-ui-serializable"` line is kept commented for
  local work). All the domain types re-exported from `src/lib.rs` and every file under `guest-js/lib/bindings/`
  come from here.
- `tauri-plugin-notifications` — push notification plugin, vendored as a **git submodule at the repo root**
  (`./tauri-plugin-notifications`, pinned to the `silent-notifications` branch). Both the plugin's `Cargo.toml`
  and the example app's `example/matrix-svelte-client/src-tauri/Cargo.toml` depend on it by **path** into the
  submodule (they must share the same source). It's a submodule (not a git dep) because its iOS Swift package needs
  the `.tauri/tauri-api` bridge generated *in the same tree* — see "Mobile push notifications" / the iOS build note.

Run `git submodule update --init` after cloning, or `cargo build`/`cargo check` fails immediately (missing
`tauri-plugin-notifications`). To bump the plugin: `git -C tauri-plugin-notifications fetch && git -C
tauri-plugin-notifications checkout <rev>`, then commit the updated submodule pointer.

`guest-js/lib/bindings/*.ts` are generated by [ts-rs](https://github.com/Aleph-Alpha/ts-rs) from Rust types in
`matrix-ui-serializable` — never hand-edit them; regenerate from that repo instead.

## Workspaces

The repo is a single Cargo workspace **and** a single pnpm workspace, both rooted at the repo root.

- Cargo: the root `Cargo.toml` is both the workspace root and the plugin package. Members are the plugin (`.`),
  the example app (`example/matrix-svelte-client/src-tauri`), and — automatically, as a path dependency — the
  `tauri-plugin-notifications` submodule. There is one `Cargo.lock` and one `target/` at the root.
  Versions of dependencies shared by the plugin and the example live in `[workspace.dependencies]`; both crates
  refer to them with `<dep>.workspace = true`, so they can never drift apart. The single shared `Cargo.lock`
  is what keeps `rustls-platform-verifier` single-copy (see the Android TLS section). `[profile.*]` is only
  honoured at the workspace root, so the example's release tuning lives in the root manifest too.
  `default-members` is the plugin, so a bare `cargo build` at the root still builds only the plugin.
- pnpm: `pnpm-workspace.yaml` lists `.` (the `tauri-plugin-matrix-svelte-api` package) and `example/*`. The example
  depends on the plugin package with `workspace:*`, i.e. a live symlink to the repo root — run `pnpm build` at the
  root after changing `guest-js/` so the example picks up the rebuilt `dist/`.
- `.cargo/config.toml` (Android/iOS target CPU features) lives at the repo root and applies to every member.
- `.taurignore` (repo root) is **load-bearing** for `pnpm tauri dev`. The app depends on the plugin crate by path, so
  Tauri watches the whole repo on top of `src-tauri`, and it reads its ignore file from the common ancestor of the
  watched folders — the repo root, not `src-tauri` as the Tauri docs suggest. The `workspace:*` link means
  `example/matrix-svelte-client/node_modules/tauri-plugin-matrix-svelte-api` is a symlink back to the repo root, so
  the shared `target/` is reachable under a path Tauri doesn't recognise as the cargo target dir; without those
  patterns every artifact cargo writes looks like a source change and dev rebuilds forever. Patterns are matched
  against the whole path (no parent-directory matching), so they need `**/`…`/**` on both ends.
- Because `tauri` is inherited from `[workspace.dependencies]`, the Tauri CLI can no longer rewrite the app's
  `tauri` feature list and prints an `Info … workspace inheritance` line on every run. It currently expects no
  features, but if `tauri.conf.json` ever needs one (isolation pattern, `macOSPrivateApi`, asset protocol…) it has
  to be added to `example/matrix-svelte-client/src-tauri/Cargo.toml` by hand.

## Common commands

Run `pnpm install` **once at the repo root**; it installs both workspace projects.

Plugin (repo root):
- `pnpm build` — builds the JS/Svelte bindings package (`svelte-package` + `publint`)
- `pnpm check` — `svelte-kit sync` + `svelte-check`
- `pnpm lint` / `pnpm format` — prettier + eslint (check vs. write)
- `cargo build` / `cargo check` — builds the Rust plugin (needs `git submodule update --init` + the git companion, see above)

Example app (`example/matrix-svelte-client`):
- `pnpm tauri dev` / `pnpm tauri build` — run/build the full desktop app
- `pnpm check`, `pnpm lint`, `pnpm format` — same tooling as the plugin package
- Mobile: standard `pnpm tauri android dev` / `pnpm tauri ios dev` once the platform projects are initialized
- iOS first build: the NSE Swift package references `tauri-plugin-notifications/ios`, whose `Package.swift` needs the
  submodule's `.tauri/tauri-api` bridge. Generate it once with `cargo build --target aarch64-apple-ios` (from the
  example's `src-tauri`) after `git submodule update --init`; tauri-build writes it into the path-sourced submodule.

There is no JS test runner wired up (vitest is a dependency but no `*.test.*`/`*.spec.*` files exist yet). Rust has a
couple of inline `#[test]`s (e.g. `reconstruct_custom_uri` in the example's `src-tauri/src/lib.rs`); run with
`cargo test`.

## Required plugin configuration

Consumers must set a `matrix-svelte` key in `tauri.conf.json`'s plugin config with: `android_sygnal_gateway_url`,
`ios_sygnal_gateway_url`, `oauth_client_uri`, `oauth_redirect_uri` (see `PluginConfig` in `src/lib.rs`).

This plugin must be initialized *after* `tauri-plugin-svelte` and `tauri-plugin-notifications` in the consuming
app's builder chain — it depends on both being ready first.

## Architecture

### Rust plugin core (`src/`)

- `lib.rs` — plugin entry point (`init()`), registers all commands, spawns the async matrix-ui-serializable runtime
  during `setup`, wires up the `LibConfig` (session, event receivers, updaters, OAuth config). Also holds two global
  `OnceLock` senders (`LOGIN_SENDER`, `AUTH_DEEPLINK_SENDER`) used to bridge frontend-triggered events into the async
  runtime, and re-exports the domain types/commands consumers need.
- `commands.rs` — all `#[tauri::command]` handlers invoked from JS (`invoke('plugin:matrix-svelte|...')`).
- `desktop.rs` / `mobile.rs` — platform split for `MatrixSvelte<R>` construction; mobile registers the native
  Android (`PushNotificationPlugin`) / iOS (`init_plugin_matrix_svelte`) plugin handles.
- `events.rs` — two-way event bridge between the frontend and the matrix-ui-serializable async runtime:
  - Outgoing (`event_forwarder`): consumes `EmitEvent`s from a broadcast channel and re-emits them as Tauri events
    (`matrix-svelte://...`) or OS notifications.
  - Incoming (`handle_incoming_events`): listens for specific Tauri events from the frontend (e.g.
    `matrix-svelte://verification-result`) and forwards them into mpsc channels the core library reads from.
- `state_updaters.rs` — implements `StateUpdaterFunctions` (the `Updaters` struct). Every state change from the
  matrix client (rooms list, active room, login/verification/recovery state, current user info) is pushed to the
  frontend by patching `tauri-plugin-svelte` stores directly (ids: `rooms-collection`, `room-store`, `login-state`
  — these ids must match the JS store classes in `guest-js/lib/stores/`). This is a known architectural cost: full
  state is serialized on every update rather than diffed/streamed over raw IPC (documented in the README's
  "Possible improvements" section) — keep this in mind before "optimizing" one call site in isolation.
- `keyring/mod.rs` — persists the Matrix session using `keyring-core` with a platform-specific backend selected at
  compile time (macOS/iOS via `apple-native-keyring-store`, Android/Windows/Linux via their respective crates).
  Sessions are base64-encoded and namespaced with a random per-app-data-dir salt file. `init_keyring_store()` is
  idempotent (`std::sync::Once`) because it must be callable both from the normal plugin `setup` (warm path) *and*
  from the Android cold-start JNI entry point (see below) — `keyring_core::set_default_store` panics if called twice.
- `utils/mod.rs` — app dir resolution and plugin config parsing helpers.

### Frontend package (`guest-js/lib/`)

- `index.ts` — the public API surface: thin `invoke()` wrappers around every command, plus re-exports of stores,
  bindings, and event/type-guard helpers.
- `stores/` — the three Svelte 5 Rune stores consumers instantiate in `hooks.client.ts`: `RoomsCollection` (room
  list), `RoomStore` (currently open room/timeline), `LoginStore` (auth/login state). Their store ids
  (`rooms-collection`, `room-store`, `login-state`) are the other half of the contract with `state_updaters.rs`.
- `bindings/` — generated TS types mirroring Rust structs/enums from `matrix-ui-serializable` (see ts-rs note above).
- `matrix-requests/` — helpers to build `MatrixRequest` payloads for `submitAsyncRequest`.
- `tauri-events.ts` / `type-guards.ts` — typed wrappers for listening to the `matrix-svelte://...` events and
  narrowing timeline/message item unions.

### Mobile push notifications (silent/data-only pushes)

This is the most subtle part of the codebase — read `example/matrix-svelte-client/src-tauri/src/lib.rs`,
`push_handler.rs`, `push_shared.rs`, and the sibling `tauri-plugin-notifications`' `nse.rs` /
`TauriFirebaseMessagingService.kt` together before touching notification code:

- **One handler, every app state**: the example app registers a single Rust handler with the notifications
  plugin's `silent_push_handler!` macro (`push_handler.rs`). It exports both the iOS NSE `dlsym` entry and the
  Android JNI entry; the plugin's FCM service loads the app's `.so` itself (named by the `SILENT_PUSH_LIB`
  manifest meta-data) and calls the handler for every data-only push — warm *or* cold-started — then posts the
  returned `NotificationData`. The handler fetches the event via
  `tauri_plugin_matrix_svelte::handle_silent_notification` (`push_shared.rs`).
- **Android cold-start init**: a Firebase-started process never ran the plugin's `setup()`, so the macro's
  `android_init` hook (`android_push_init`) replays logging, the rustls platform verifier, and
  `init_keyring_store` before each handler run. tao (Tauri ≥ 2.12) initializes `ndk_context` in the activity's
  `onCreate` and aborts if it is already set, so the hook only *borrows* it to build the keyring store (init →
  `init_keyring_store` → release). `MainActivity.onCreate` calls `claimNdkContext()` before `super.onCreate`, which
  switches the borrowing off under the same mutex — Android may reuse a push process to launch the app, and vice versa.
- **Badge pushes**: a data message without `room_id`/`event_id` is the homeserver's unread-count update; when
  `unread == 0` the handler returns `SilentPushResponse::ClearActive` and the plugin clears the notification
  shade plus its stored conversation histories (Android only — iOS badge pushes never reach the NSE).
- Android accumulates same-room notifications into one `MessagingStyle` notification (keyed by room id); iOS keys
  by event id and groups by conversation thread instead — this difference is intentional, not a bug.

### Android TLS / certificate verification

`matrix-rust-sdk` dropped its Android `WebPkiServerVerifier` special case, so rustls now delegates to
`rustls-platform-verifier`, i.e. Android's Java verifier. Things to keep in mind:

- **Revocation / cleartext**: the verifier's `PKIXRevocationChecker` downloads CRLs over plain HTTP. Since
  `rustls-platform-verifier-android` 0.2.0 (pulled in by `rustls-platform-verifier` 0.7.1), the AAR bundles a
  manifest with its own `android:networkSecurityConfig`, which allows cleartext only for the CRL hosts listed in
  the CCADB. The manifest merger adds it to the app. The example therefore has **no**
  `network_security_config.xml` and no `networkSecurityConfig` attribute. Don't add either back: an app-level
  one replaces the library's and brings back false `invalid peer certificate: Revoked` errors. A CA missing
  from the list is fixed upstream (rustls-platform-verifier#221), not here.
- **Kotlin component**: Gradle fetches the AAR from the GitHub-hosted Maven repo (`maven-archive` branch), no
  longer from the crate's bundled `maven/` dir. `gen/android/app/build.gradle.kts` reads the version of the
  `rustls-platform-verifier-android` crate from the root `Cargo.lock` (`RustlsVersion` `ValueSource`) and forces
  the unversioned `org.rustls:rustls-platform-verifier` dependency to it. The group really is `org.rustls`: the
  upstream README's `rustls:` coordinate is a typo, and with it the version rule never matches.
- **jni 0.21 vs 0.22**: `rustls-platform-verifier` 0.7 uses `jni` 0.22 (renamed `jni_022` in the example's
  `Cargo.toml`), while wry and `tauri-plugin-notifications` are still on 0.21. `init_platform_verifier` in
  `push_handler.rs` re-wraps the raw `JNIEnv`/context pointers and calls `init_with_env`. It is the single entry
  point used by both the app `setup` and the silent-push cold path. It is idempotent, so no extra latch is needed.
- **Single copy**: the example app must resolve `rustls-platform-verifier` to the same version reqwest does.
  With two copies in the tree, the app initializes one while matrix-sdk uses the other, and all TLS fails. The
  shared workspace `Cargo.lock` guarantees this. When bumping, check `cargo tree -i rustls-platform-verifier
  --target aarch64-linux-android`, and run `cargo update -p rustls-platform-verifier@<old>` if reqwest stayed
  on the old version.

### Custom `mxc://` media protocol

The example app's `src-tauri/src/lib.rs` registers an async URI scheme handler for `mxc://` to stream Matrix media
(including encrypted attachments, via query params for key/iv/hash) straight from the SDK into the webview. Android
and Windows can't route a fully custom scheme, so requests there arrive as `http://mxc.localhost/...` and get
rewritten to the common `mxc://...` form before parsing (`android_windows_to_common_uri`).

### Permissions (`permissions/`)

Tauri ACL definitions per command, one `allow-*` toggle per command in `permissions/default.toml`/`autogenerated/`.
When adding a new `#[tauri::command]` in `commands.rs`, it also needs a corresponding permission entry and to be
registered in `tauri::generate_handler!` in `lib.rs`.
